# 架构诊断、决策与变更 SOP

先选择结构诊断、方案设计、实现审查或迁移复核；任务规模决定工件深度。局部修改可用简短决策，不要求画全套图。

1. **现状和约束。** 从入口、调用者、配置/数据权威源及运行方式建立现状；区分已读事实、设计目标和未知。列作者已确定的技术/目录/双库/权限边界，不重新选择已定参数。
2. **责任与依赖图。** 按“哪个模块负责何种变化”归属，画必要的系统上下文/模块图；标入口、应用操作、领域规则、持久化和派生投影的依赖方向。每条配置、评分、状态与权限规则列唯一维护点和所有消费者。
3. **追踪契约。** 至少追一条代表读链和写链：请求→身份/范围→服务→数据/事件→返回/投影，写清版本、错误、重试和部分成功语义。共享服务不等于共享所有能力，MCP等只读入口维持能力限制。
4. **比较关键备选。** 对真正影响维护/兼容/数据的取舍给问题、驱动因素、方案、优缺点、选择理由和后果。比较现状/最小方案和必要的扩展；不为形式虚构备选，不能仅以“灵活/可扩展”推荐新层。
5. **演进推演。** 用专题方法检查配置/结构迁移、并发、幂等、事件与投影、权限、历史兼容和失败恢复；列旧调用者如何继续、哪些数据需转换、怎样验证语义与原值、如何识别冲突。
6. **实施与回退。** 切成可验证批次，列前置、改动归属、受影响接口/生成物、验收、回退触发与保留内容。处理一处变更多处手工同步的问题；不以复制第二套实现保兼容。
7. **以证据复核。** 检查导入/调用方向、真实入口、打包后的资源、正反例和当前指纹。源码/模型图只证明相应层，不冒称真实DB、宿主和用户路径已验；对major给定位、影响与具体修法。

## 报告映射

ownership为责任表；dependencies为图及允许/禁止方向；read_path/write_path为具体追踪；compatibility为旧调用者及迁移验证；rollback为分批回退；acceptance为代表场景与证据；experience_application说明本任务的相关旧案例与差异。决策可写入对应字段，不额外新建状态或重复报告。

设计ready仅表示当前方案可推进，真实集成待验保留pending；既有实现中已复现的破坏性行为不能以“未来优化”延后当前修复。
