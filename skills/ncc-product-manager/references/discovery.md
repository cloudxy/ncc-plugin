# 需求证据与优先级方法

## 证据表

为关键判断记录“主张｜证据类型｜出处/版本｜不确定性｜会改变什么决定”。作者明确选择可作为本项目约束；代码只能证明实现；Mock只能证明替身环境；使用数据须给样本与统计口径。没有研究时写“待验证假设”，给最小验证动作，不擅自虚构用户画像或指标。

把方案词还原为任务：例如“增加世界观后台”须问清是查找设定、批量整理还是编辑冲突；“下一章”须明确当前书/卷/位置和完成后的可采用状态。明确缺陷已有作者证据时，直接设计修复，不为形式上的发现流程再次拦住用户。

## 决策与切片表

对确有取舍的候选列：目标覆盖、作者操作、前置依赖、实施/维护成本、数据与回退影响、未验证假设、推荐理由。排序优先说明会造成什么损害，不能只按开发便利或页面数量。技术债若导致多处修改、规则分叉或恢复困难，可以成为本批价值。

纵向切片例：“当前卷可完整导出并返回校对位置”，包含范围确定、分页/修订集合、产物生成、失败重试与返回。只做导出按钮、数据库表或空页面都没有闭合这条任务；也不为此要求先维护全部本体。

## 验收追踪

每个需求标识关联“条件/输入版本→用户动作→期望成果→观察办法→实际结果/待验”。同时检查至少一个适用边界和恢复场景。设计验收写将如何测；交付验收写实际做了什么；不能把两者混成passed。测量可用任务完成率、人工操作数、恢复后保留内容和耗时分布，必须给样本来源与基线。

GOV.UK的方法只提供需求、优先级和验收的思考参考，不移植政府项目审批、周期或固定方法。来源见[索引](sources.md)。
