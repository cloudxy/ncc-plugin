# 产品发现、决策与交付 SOP

按本次目标选择入口：需求不清从“任务证据”开始；明确修复可直接核对证据与范围；方案评审重点做备选和验收；交付复核从验收追踪。缺少非关键资料继续给有边界结论，缺少决定性资料标blocked并说明为何改变结论。

1. **任务证据。** 写使用者、触发、现有路径、期望成果、当前障碍；把作者明确指令、源码观察、实际使用数据和假设分开，记录来源及时间。不能把某页存在推断为用户任务完成。
2. **问题拆解。** 沿“入口→准备→执行→检查→采用/保存→恢复”追踪当前任务，标哪些步骤已有证据、哪些只是设计；问题写成可观察差距。资料治理任务按自己的目标走，不额外塞入写章流程。
3. **方案取舍。** 至少在存在真实取舍时比较沿用现状、最小改动和较大方案的收益、作者操作、技术依赖、维护代价、风险和可回退性；简单明确缺陷无需虚构三个方案。推荐须说明为何满足目标、哪些代价接受。
4. **优先级与切片。** 先处理丢稿/越权/不能完成任务等阻断，再比较受影响用户、任务频次、损害、证据可信度、依赖和成本。没有规模数据不用虚构RICE分数。切成能从入口走到可采用成果的纵向交付，附非目标、后续项、触发条件和负责人；不通过拆批次消失当前承诺。
5. **验收设计。** 每项需求关联场景、操作、可观察结果、失败/恢复、所需环境与证据。明确大数据范围、分页、人工并发、取消、重试等实际适用边界；没有用户基线先给测量方案，成功率/耗时/操作数不可编造。
6. **交付复核。** 对每条承诺定位实现、调用者、产物和当前版本证据。方案、实现、接线、行为、宿主加载分别标状态；作者另行测试的部分保持待验。对完成差距给具体修法或有归属的待办。
7. **反馈收敛。** 用真实失败和新约束更新原需求及优先级；明确哪个假设被证据支持或推翻，经验回到共享案例候选，不因一次成功推广为全局规则。

## 报告映射

author_task承接步骤1–2；value解释结果价值；scope给切片/非目标/依赖；priority给排序及取舍；acceptance给步骤5–6的追踪与测量。experience_application只写最相关案例的适用差异，不复述全部SOP。

ready只表示本次范围的需求/方案可推进；交付复核ready要有该范围实际观察。major必须列定位、证据、影响和可执行修法；决定性输入缺失用blocked。不要把“采用最佳实践”“专业后台”作为结果。
