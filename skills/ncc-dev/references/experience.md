# NCC 工程经验与角色能力

本文件保存本项目能复用的诊断方法。既定技术选型和用户偏好适用于NCC，不推广成所有项目的规则。历史缺陷、产品缺口和合成风险分开陈述；“待验”不等于已失败。已修问题不再描述为当前故障。

## 已发生的问题及可执行经验

| 编号与性质 | 问题和原因 | 下次必须能做什么；如何判断有效 |
|---|---|---|
| E01 产品缺口 | 已有默认创作台，但通用实体选择最多200项，不足以证明长篇卷章可用；资源后台完成也不能证明创作流程完成。 | 先复述作者当前任务，追踪入口到可采用成果；为长篇分页、续写位置和上下文返回定义可操作验收。独立资料治理仍可使用，不把资源完整性变成写作前置。 |
| E02 实施缺口 | 四工程职责曾停在方案，作者追问后才完成接线。规划、代码、接线、行为、实际加载被混称“完成”会让交付失真。 | 承诺一项能力就定位实现、调用者、产物和证据；缺哪个就报告哪层待办。沿原任务继承授权与范围；不能用拆批次隐藏当前已承诺内容，也不能把作者留待专项的测试擅自标通过。 |
| E03 配置和归属 | 作者反复明确普通人不应操作终端环境变量，私有配置应归config，并指定Dynaconf。起初目录与统一装配没有同时落实。 | 追踪初始化、服务、CLI、MCP、测试和打包消费者；配置归属与入口默认一致，初始化保留原值，文档和错误给出可执行恢复。参考hcdataspider的方法，不复制其凭据。 |
| E04 复用和机制 | 项目曾需要整理大文件、公共连接/配置/客户端逻辑及registry来源；分目录不能自动解决规则重复。 | 给每条配置、授权、评分和阶段规则指定唯一维护点，追踪一条读链及写链；入口复用应用服务。通用存储机制支持扩展，作者界面按作品语义组织；不增加空层或按每类设定建表。 |
| E05 独立复现缺陷，已修 | config迁移先link后unlink，会删除并发保存的新文件；TOML文本替换可改到多行字符串里的假入口，解析仍成功。 | 迁移先定义原值、文件身份、并发替换和失败后的保留条件；不能“检查存在再覆盖/删源”。结构化修改比较“原对象仅指定语义变化”的期望，测试合法但有干扰内容的输入。解析成功和正常路径用例均不够。 |
| E06 已确定的运维约束 | 作者纠正多库管理方向，已确定唯一正式/正式库-test；真实连接资料仍缺失，工具可发现而connected=false。 | 维持既定连接和唯一测试库，以范围/标识隔离作品与任务；不能猜账号或为验证另建随机库。分别报告配置、连通、授权读取、写入、恢复、性能证据；未连库不承诺已可用。 |
| E07 合成反例，非已发生丢稿 | 角色回归中发现旧AI覆盖人工新稿、索引失败删除正文、重复回写增生事实的错误提案；没有证据证明这些事故已在真实作品发生。 | 明确生成基线和人工最新稿，采用校验版本、事务/修订/审计和持久幂等；投影失败允许重试，正文保存状态单独显示。按并发编辑、重放和部分失败验收，不能只看成功按钮。 |
| E08 已有产品约束 | 作者要求AI评分、自动化和已授权自动定稿；简化交互容易被误解为只看分数即可采用。 | 沿现有评分/闸门/授权契约执行，分数用于质量判断，不能代替硬缺陷、授权范围和版本检查。有效托管资格保留，必要作者创作决定保留；不发明新阈值、不要求重复确认。 |
| E09 证据边界 | 多轮静态、Mock或代码交付完成，真实PG和五宿主新会话仍待验；自查也曾需要与独立评审分开。 | 每项结论写清对象版本、环境、实际观察和未验项；旧证据不冒充新候选，工具发现不冒充连接，改文件不冒充新会话加载。同会话多职责如实记current_session。 |
| E10 独立复现缺陷，已修 | 无engineering_contract曾直接成功，允许新任务绕过报告；只查任务自身base又误伤先冻结base后创建的旧任务。普通检查还隐藏角色待办。 | 默认不把缺字段当旧版证明；用实际历史和适用范围验证兼容，已采用契约不能删字段回退。新增负例必须配合法历史正例；pending/failed/blocked要可见，不能用统一“失败”抹平原因。 |

## 四角色要形成的能力

| 角色 | 能力变化 | 本次任务中的具体交付 |
|---|---|---|
| 产品经理 | 从列功能转为判断作者价值、兑现范围和证据级别 | 说明任务入口、可采用成果、主辅线、优先级/非目标；指出当前方案少了哪条闭环及验收方法。资源独立任务按其用户目标衡量，不硬塞写作步骤。 |
| 产品设计师 | 从列页面转为设计完整操作与异常恢复 | 给默认路径与上下文、编辑/保存/采用的区别、并发/过期/失败状态和恢复动作；以实际任务检验，不以配置项和按钮数量衡量专业性。 |
| 架构师 | 从移动文件转为控制归属、规则来源和演进风险 | 列唯一维护点、消费者、读写依赖、变更语义和回退；迁移、兼容与授权边界有正反例，避免把当前案例限制成全局硬编码。 |
| DBA | 从会连接和建表转为管理完整数据生命周期 | 核对既定连接/双库、事务/历史/并发/权限、查询规模与恢复；用实际证据分层放行，无法实测时交付前置条件和明确测试办法。 |

## 执行与积累

在既有角色报告的experience_application中选择本任务最相关的1–3条：案例编号与触发条件 → 已读证据及与旧案例的差异 → 本次取舍和处理位置 → 可观察验收及未验项。没有相关案例时解释边界，不生套所有条目。只写编号或“已学习/最佳实践”应退回。可以引用报告已有交付位置，避免重复正文。

经验应用是原角色交付的一部分，不增加作者审批、每章角色或额外报告。注册表统一维护必读路径和必交付字段；既有packet绑定经验字节，record检查缺项，输入变化后重派。字段校验不能证明推理质量，需真实新任务验证：能识别问题变体，也能接受符合约束的设计，不能对所有方案一律退回。能力验证不承诺模型永久记忆或已经熟练完成真实DB运维。

新增经验先有具体问题/复现或明确来源，记录已修/风险/待验边界，再判断是否改变诊断和验收；重合经验合并到现有条目，不按每次事故增加一条全局禁令。改变职责或判定方式时按开发工作流隔离验证，记录对应反例及合理方案，再在已授权范围整合。当前验证与新场景结果见[经验转化任务](../../../docs/tasks/2026-10-19-engineering-experience.md)。

实施顺序：整理上述证据 → 注册四角色读取和必交付 → 同步角色/共用协议与生成物 → 受影响脚本和输入新鲜度检查 → 新场景实际执行/独立评审 → 整合并核对候选。回退仅本批规则/读取/生成物，不动数据库、真实配置或已修迁移代码。
