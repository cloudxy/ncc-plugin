# 产品策略 · NCC 创作后台

> 产品层文件（负责人：pm）。只记长期判断与已验收的产品边界。
> 证据日期：2026-11-25。来源：作者原话、[小说创作工作台重构设计](../designs/storage/novel-studio-overhaul.md)、[数据后台使用指南](../guides/data-console.md) 及 2026-11-22 至 2026-11-25 多轮全栈验收结论。没有线上使用量统计，不编造次数。

## 1. 一句话

为正在写长篇的作者兼出品人，在已登录的 NCC 后台里，把写作、大纲、设定、公共陈列、市场约束与一键成稿导出放在同屏可及的地方，让兼容 HTTP 网关或本机 CLI 订阅驱动的 AI 按可拆可合的工序出候选，由人做方向、内容和质量裁决。

## 2. 目标用户与任务（JTBD）

| 人群 | 他们要完成的任务（当…时，我想…，以便…） | 过去做法（替代品） | 替代做法的代价 | 频次 |
|---|---|---|---|---|
| 作者兼出品人 | 当我写一章时，我想同时看到细纲、设定、伏笔、暗线和市场约束，切换防剧透的「读者此刻」视角，让 AI 只执行我勾选的工序，并随时一键导出 EPUB/TXT/MD 成稿 | 初版后台将 14 个入口平铺，工序打包在黑盒「开始处理」里，后台导出只有工程备份包 | 上下文频繁跳页；无法只推细纲或只定向返修；拿不到干净成稿 | 每次写作会话 |
| 同一人的协作与维护时刻 | 当我管理模型路由、添加协作者、归档空间或处理保存冲突时，我想用可读名称和受管向导完成操作，清楚知道原稿仍在且秘密设定不会外泄 | 手工复制 UUID、手工查终端 OAuth 状态、阅读裸 JSON 审计与评估记录 | 易操作出错；权限或并发冲突时担心丢稿 | 随配置、协作与保存发生 |

**服务对象：** 作者本人及受邀协作的审校/研究成员。

情感层：稿纸应像安静可靠的私人书案，裁决权始终留在手边。社会层：内部私有创作工具，不设公开社交展示。

## 3. 核心价值与 Aha 时刻

| 项 | 内容 |
|---|---|
| 核心价值 | 在当前章内完成方向、内容和质量裁决，AI 候选未经作者确认绝不覆盖正文，秘密设定与未来伏笔严格按权限和阅读视角隔离 |
| Aha 时刻 | 创作台右栏同时给出候选分数、依据，以及「采用当前候选」和「放入编辑器继续修改」；顶栏可一键导出干净 EPUB 3 / TXT / Markdown 成稿 |
| 到达 Aha 的最短路径 | 已有范围和章节：创作台 → 选章 → 勾选工序开始处理 → 查看质量把控并裁决。无范围时先新建作品或资料库 |
| 让用户持续使用的理由 | 正文修订、立书档案、`01-设定/` 资料卡、伏笔承诺与 CLI 工作副本双向幂等同步，随时接续不丢账 |

签名时刻是一键专注模式：四周导航与面板收起，只留宋本稿纸、汉字计数、目标进度与退出按钮。

## 4. 为什么是我们（差异化）

| 替代品 | 它做得好的 | 它做不到的 | 我们如何做到 |
|---|---|---|---|
| 初版 NCC 数据后台 | 路由、细粒度权限、草稿、P1–P5 评分底座完备 | 写作上下文分散、管理菜单平铺、缺少成稿导出与零 UUID 治理 | 在同一套实体和事务底座上重排六大创作空间与三组折叠高级管理，零新增物理表、零改评分策略哈希 |
| novelWriter / Manuskript / bibisco 等桌面工具 | 卷章树、细纲卡片墙、人物设定卡体验成熟 | 不接 NCC 的范围权限、历史修订、三本账和 P1–P5 审评策略 | 仅吸收布局与信息组织思想，独立基于 React + FastAPI + PostgreSQL 实现，零外部源码引用 |

## 6. 北极星与护栏

成败以端到端真实数据库与真实 Chromium 浏览器走查为准，不依赖虚构埋点。

| 层 | 指标 | 为什么是它 |
|---|---|---|
| 北极星（走查） | 统一浏览器回归套件 `scripts/dev/run_browser_suite.py` 全套通过（覆盖日常工作台、撤权恢复、六大空间、自动定稿、升级治理与 CLI 桥接） | 直接验证「同屏能写、能核、能裁决、能导出、能协同」 |
| 护栏 | `G-DRAFT`：冲突或断网后编辑器原稿保留；`G-ACCESS`：WCAG 正文对比度 `≥ 4.5:1`、全站字号 `≥ 12px`、`1440 / 768 / 375` 零横向溢出；`G-POLICY`：`policy.json` 字节恒定 | 防止界面升级牺牲文稿安全、可读性或审稿口径一致性 |

## 8. 不做什么（战略边界）

| 不做 | 理由 | 何时重新考虑 |
|---|---|---|
| 新增物理表、新增数据库库名或修改 `policy.json` | 严守 `ncc-pro` / `ncc-dev` 双库与评分策略哈希稳定 | 既有实体/修订/配置模型确证无法表达新业务时由作者另行授权 |
| 新增前后端第三方运行时依赖 | 保持部署轻量与供应链可控 | 作者明确批准新依赖时 |
| 在浏览器内联渲染 SVG / HTML 附件或回传订阅明文令牌 | 防范同源 XSS 与凭据泄露 | 不放开（安全红线） |
| 任意拖拽有向无环图编排或多人逐字实时协同光标 | 五段式工序已覆盖长篇网文核心循环，避免过度工程化 | 作者明确提出实时合写需求时 |
| 将私有书稿、`novels/` 或本机证据写入公开文档 | 私有内容硬约束 | 永不放开 |
