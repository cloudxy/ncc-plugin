# 文档组织规范

状态：现行规范。本文规定 docs/ 的目录职责、文件归属、命名与生命周期；开发阶段和证据要求仍以[开发工作流](workflow.md)为准。2026-10-16 完成归属收敛：原散在 `workflow/` 的设计记录与治理规范已迁入 docs/，`workflow/` 只保留现行规则与生成视图。

## 目录与职责

```text
docs/
├── README.md                      # 全局导航：入口、模块设计状态、未执行计划与待办
├── guides/                        # 使用说明：操作、命令、常见问题（面向使用者）
├── engineering/                   # 现行规范：开发、测试、交付、文档、外部来源治理（面向维护者）
│   ├── workflow.md                # 开发路径、阶段、证据与交付的唯一规范
│   ├── documentation.md           # 本文
│   └── source-vetting.md          # 引入外部 skill/语料/工具前的筛查与黑名单
├── designs/                       # 设计依据与升级方案，按模块分目录
│   ├── deconstruction/            # 拆书
│   ├── engineering/               # 开发流程与工具
│   ├── memory/                    # 记忆、设定类目、拆书学法与自进化
│   └── preparation/               # 创作前准备与通用素材库治理
├── tasks/                         # 活动任务：任务号、决定、阶段、恢复点
└── evidence/
    └── <任务号>/                  # 输入、观察、日志、评审与结果
```

用途是一层分类，模块是设计文档的第二层分类，任务号是执行记录与证据的关联键。目录只在出现实际文件时创建，不预留空目录；模块内部文件多到导航困难时再按子功能分目录，不按日期平铺。

## 归属判定

现行规则的唯一事实源在 `workflow/`（registry/ 分片、registry.json 兼容生成视图、principles.md、architecture.md）与 `skills/`、`agents/`、`commands/`；docs 不复制规则正文，只放导航、说明、规范、设计与执行记录。新增一份文档时按性质判定，一次判定只落一个目录：

| 这份文档是什么 | 去哪里 | 边界 |
|---|---|---|
| 面向使用者的操作说明 | `guides/<主题>.md` | 不复制规则表；不写未实施功能 |
| 当前有效的维护契约或治理规范 | `engineering/<主题>.md` | 写"现在怎么做"，不写成设计方案 |
| 未实施的升级方案（含分阶段计划） | `designs/<模块>/<主题>.md`；同一模块整体升级可用 `upgrade.md` | 不能在指南或规范里写成已可用 |
| 已实施的设计依据留档 | 同上，状态标头改为已实施 | 留档不承担现行规范职责 |
| 活动任务 | `tasks/YYYY-MM-DD-<主题>.md` | 进度、授权、精确范围、候选指纹；不复制设计全文 |
| 验证证据 | `evidence/<任务号>/<检查名>.md` 或 `.log` | 实际输入输出、环境、覆盖、缺项；不能变成现行规则 |

两类易混情况：设计与规范合体时看它今天约束什么——约束当前行为（如 source-vetting 的七项检查）进 `engineering/`，只解释取舍与计划进 `designs/`；跨模块的设计放主要改动所属模块，不建"通用"或"杂项"目录。

`workflow/` 与 docs 的边界（收敛规则）：`workflow/` 只留现行规则——registry/ 分片、由其生成的 registry.json 兼容视图、principles.md、architecture.md。设计记录、审查记录、升级方案一律进 `docs/designs/<模块>/`，避免同一份取舍说明在运行规则目录和文档目录各存一份。

## 命名与状态标头

- 长效指南和当前方案用稳定主题名，便于外部链接与搜索；任务与证据用任务号，日期区分执行批次。
- 每份 designs 文档开头标明：状态（方案候选／已实施留档／已被替代）、适用版本或基线、关联任务、授权边界。guides 与 engineering 标"现行"与最近实质更新即可。
- 标题行不写版本号（版本只在 plugin.json，由检查器核查）。
- 设计与实施计划可在一份方案内分节维护，结构任务的 `spec`、`plan` 可引用同一文件。
- 同一目标只维护一份当前方案、一份活动任务记录；新的执行批次开新任务号。

## 生命周期

- 方案候选 → 实施任务完成后改标"已实施留档"（稳定操作说明更新进 guides，现行契约更新进 engineering）→ 被新方案替代时删除并清理引用，历史由 Git 保留，不建迁出占位页。
- 任务记录：交付候选提交后，若其证据仍是当前发布依据，记录迁入 `evidence/<任务号>/task.md` 退出活动目录（先例：2026-10-12-ncc-dev）；未提交的已验收任务留在 `tasks/`，便于 continue 恢复与提交前核对。没有现行作用的旧任务和证据由 Git 历史保存。
- 未执行的计划与待办集中登记在[文档导航](../README.md)的"未执行的计划与待办"，随任务完成更新；不在别处另写第二份计划清单。
- 迁移文件时先更新全部引用（含 skills/workflow 内的反引号路径与 Markdown 链接，由 `check_plugin.py` 核查）；`evidence/` 冻结报告字节不动，其历史路径不参与现行链接检查，路径变动不能把旧证据重新标为新候选通过。

## 模块清单与扩展

现有模块：`deconstruction`（拆书）、`engineering`（开发流程与工具）、`memory`（记忆与自进化）、`preparation`（创作前准备与素材库治理）。预留命名（出现实际设计文件才建目录）：`writing`（写章）、`review`（审稿）、`materials`（素材）、`eval`（评测）。新增模块时同步更新本清单与[文档导航](../README.md)的模块表。

## 维护与查找

1. 新增前先查模块和活动任务，避免同一目标出现并行方案或并行记录。
2. 全局导航只链接主要入口、现行方案与未执行计划；文件增加后，必要时在模块目录增加 `README.md` 做局部导航，避免全局索引复制所有细节。
3. 链接使用相对路径；脚本、技能里的查找路径必须随目录迁移同步。
4. 活动文档中的路径和链接由 `check_plugin.py` 核查；证据存在性、哈希和候选新鲜度由 `check_dev_workflow.py` 检查。
5. 搜索先限定用途或模块，如 `rg --files docs/designs/deconstruction`；按任务号可同时找到 `tasks/` 的记录与 `evidence/` 的验证。
6. 真实书稿、材料和私人会话不进入任何文档目录。
