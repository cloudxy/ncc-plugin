## 为什么这些问题会成组出现

Git 历史显示，b238bff 先建立八阶段骨架；1a65b3b 增补“借思想、不照搬”；eee4297 再增补双分支与 grill 家族分析。后两次主要往原框架添加理念，没有同步重写阶段通行条件、授权继承、失败处理和验收面。因此“按量级走”与“人人过八关”、“双端协作”与“只读克隆”等规则留在同一文档里。

zcode 会话又显示，早期接线先经历用户级安装、拆分开发仓库等调整，作者多次纠正后才确定终态。方案把这些纠正提炼为 SSOT 口号，却没有给每个决定保留来源、范围和仍允许的行为，遂把“避免真相分叉”收紧为“只能一处编辑”。

更深层的共性是：先拿到一组看起来完备的方法名，再为本项目找类比；没有先以本项目的失败场景检验流程。对 ncc 而言，规则的输出由模型执行，代码测试、模型行为与宿主接入的证据天然不同。只列一个“全绿”闸门会遮蔽这些差异。

## 本地实证

核查时 novel_wk HEAD 为 eee4297，工作树干净；zcode 独立克隆 HEAD 为 b238bff，工作树干净。说明本地消费克隆当时没有包含后两次方案修订；这只证明本地版本差异，没有查询远端实时状态，也不推断 zcode 当前会话实际加载了哪一版。

当前主工作树 core.hooksPath 为 .githooks。普通 Git 克隆不携带本地 config，不能据此认定另一克隆也已启用钩子。pre-commit 实际检查 origin/main 是本地 HEAD 的祖先及暂存路径；pre-push 对 main 做祖先检查，未运行测试或模型评测。

在修订前运行 check_plugin 得到六项失败：三个拟新增文件被写成已存在的路径引用，另三项使用章节序号引用，违反现有按名称引用规则。build_docs --check 通过，机械层六章通过。说明原稿自己的“一致性不回归”成功标准已经未满足；不能将这些既有失败算作后续实现引入。

拟建路径在修订稿中明确标为计划内容，不伪造目标文件来消除报错；章节引用改用标题名称。修订前全量 unittest 运行 115 项，唯一失败是 test_plugin_self_check，与这六项一致性错误对应；耗时 165.405 秒。完整修订后验证结果记在文末。
