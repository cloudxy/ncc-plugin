# 小说创作主线与工程职责

状态：作者已明确要求执行四类工程角色接线，按[角色实施任务](../../tasks/2026-10-19-engineering-roles.md)实施和验证；配置修正见[配置任务](../../tasks/2026-10-19-dynaconf-data-access.md)。后续卷章界面与完整创作路径改造仍为候选。本方案不修改创作判据或替代现有十二个创作角色；接线、行为验证与宿主新会话分别记录。

## 1. 定位与问题诊断

NCC首先帮助作者从想法推进到可采用、可继续的小说成果。资源管理为创作提供可检索、可追溯、可复用的材料；它也可独立使用，但不要求普通写作先完成百科、类型定义或关系管理。数据库与后台能力的多少，不作为创作功能完成的判断标准。

本次基于现有源码和规则进行判断，未做真实作者可用性测试：

| 观察 | 依据 | 结论 |
|---|---|---|
| 配置归属不统一 | 原共享路径指向根.env，模板和MCP又分别持有对应位置 | 目录原则没有落实为共享路径和迁移约束；本轮修正为config目录 |
| 创作入口已在前台 | Shell默认渲染CreativePage，作品资料与待办一级入口、高级管理折叠 | 已有创作优先的方向，不能说完全没有产品设计 |
| 写作操作仍暴露通用对象模型 | CreativePage从单页最多200项的通用实体搜索生成编辑对象选项，并提供评分方案选择 | 长篇作品的卷章导航、续写位置和默认评分选择需要产品化；现状不等于专业写作流程已验收 |
| 有工程阶段，缺少职责工件 | 开发工作流已有D0–D7；roles注册的是十二个创作角色 | 缺的是软件工程四类职责的明确承担、前置结论和验收闭环，不只是缺四个名称 |
| 有数据库约束，缺少真实运维证据 | 代码已有唯一-test、迁移、权限、历史及备份入口；既定连接来源仍缺失 | 已有部分DBA实现能力；真实只读、落库、恢复和性能没有证据，不能宣布DBA能力完备 |

架构问题应由维护流程提前发现，而非每次等待作者指出。一个开发会话可以承担多个职责，但要分别提交结论，不能把同一份自查标成多位独立专家评审。

## 2. 作者路径与资源路径

主入口保持作品和当前写作位置：继续当前章、创建下一章、直接编辑、给出修改意见、查看成果和评分、采用或按已有授权定稿。立书、立骨、连载、复盘和收束沿用现有状态机；不为新后台复制一套阶段与闸门。

```mermaid
flowchart LR
    A[作者目标或直接编辑] --> B[当前作品与卷章]
    B --> C[创作任务调度]
    R[资料与设定服务] -->|检索本次需要的上下文| C
    C --> D[生成、检查、评分与有限修订]
    D --> E[作者审核或既有托管授权]
    E --> F[正式内容的新修订]
    F -->|自动回写事实、关系和索引| R
    F --> B
```

资源更新中的歧义、推断和未解析引用保留候选；没有歧义的已授权更新按现有业务规则执行。保存正文成功后，异步索引失败可重试，不得伪称索引已经同步，也不能让索引故障导致已保存正文丢失。具体评分、版本与授权规则只引用[创作自动化设计](../storage/creation-automation.md)，不另写阈值。

产品界面分层：

- 创作层：书架、作品进度、卷章导航、编辑器、AI修改、成果对比及采用；当前作品的常用设定可就地查看和维护。
- 支撑层：资料检索、设定卡、关系、时间线、地图、拆书成果及来源；从创作上下文进入时保留作品、章节和返回位置。
- 管理层：本体定义、成员权限、审计、运行、维护和导入导出；普通写作不需要经过这些页面。

上述是目标信息架构，现有页面能力不能直接视为以上全部流程已完成。

## 3. 四类工程职责与能力证据

以下职责属于项目开发，不加入每章写作派单，也不把产品经理等同于小说经理、把产品设计师等同于世界观设计师。主开发入口仍是ncc-dev；派单方式遵守宿主及作者的代理授权，没有并行代理能力时可顺序执行并如实标注自查。

| 职责 | 进入条件与输入 | 必须交付 | 验收方式 |
|---|---|---|---|
| 产品经理 | 新功能、范围变化；作者目标、当前旅程、已知问题 | 目标用户与任务、主/辅线归属、优先级、最小交付、非目标、可观察验收；说明哪一步变简单 | 用实际作者场景走通；没有改善创作或明确资源任务的新增管理环节退回；“多了页面/表/接口”不算价值 |
| 产品设计师 | 用户路径、页面或交互变化；需求与既有界面 | 路径和原型、默认操作、状态与文案、直接编辑/返回/恢复规则；空白、加载、失败、权限、过期与未保存状态 | 从入口完成任务，核对键盘、自动保存、错误恢复、上下文保持和不必要确认；不以截图好看代替可用性 |
| 架构师 | 跨模块、契约、配置、依赖或存储变化；需求与设计 | 模块责任与依赖、唯一事实源、公共契约、兼容和迁移、失败边界与回退；用简短决策记录说明备选及取舍 | 追踪至少一条读链和一条写链；列出修改一个配置/规则需要改哪些产品实现；重复业务规则、入口各自拼配置、无归属模块退回 |
| DBA | schema、查询、数据写入、连接、权限、迁移或恢复变化 | 数据生命周期和范围、正式/-test约束、事务/CAS/幂等、约束与索引、权限和秘密处理、备份恢复及迁移计划；无DDL变化也明确连接/查询影响 | 在既定连接和唯一-test执行实际事务与冲突样例；按代表查询EXPLAIN和实际数据规模核验；恢复演练证明可恢复，不能仅凭脚本存在通过 |

共同行为要求：先检查项目已有实现和约束；列出具体反例、证据与修改办法；未知项写待验；发现影响主线、数据安全或不可逆操作时给出影响和处理范围；禁止用“遵循最佳实践”“保证可扩展”代替设计。

能力验证用具体任务，而非只读角色说明：

| 验证任务 | 合格结果 |
|---|---|
| 配置位置调整 | 架构师定位所有消费者，提出单一路径和兼容迁移；DBA证明参数原值保持；重启后MCP和非MCP使用同一连接选择 |
| “接着写下一章” | 产品经理定义续写结果；设计师给出默认位置和最少操作；架构师证明使用现有阶段和闸门；DBA证明采用生成新修订并保留历史 |
| 作者在生成时修改正文 | 设计师明确显示人工新稿和旧基线结果；架构师隔离版本；DBA验证冲突拒绝；不覆盖作者最新内容 |
| 索引失败后恢复 | 产品经理区分正文已保存与检索暂不可用；设计师给出恢复状态；架构师安排可重试投影；DBA验证重复回写不增生事实 |

每份结论记录承担者/会话、输入版本、观察、决定、未验范围和证据位置。实现者不能把自己的结论称作独立评审；真实数据库结果与Mock结果分开记录。四个角色的名称本身不能作为验收证据。

## 4. 架构与数据责任落点

沿用现有单项目和分层代码，先补职责和接口，不立即引入微服务或四套实现：

| 责任 | 当前归属 | 本方案后续要求 |
|---|---|---|
| 阶段、闸门、创作规则 | workflow/registry、skills及原文件流程 | 核对后台/文件模式一致性；不得各维护一份判据 |
| 创作任务与评分执行 | ncc_data/creation、应用服务 | 作者指令形成可恢复任务，固定输入版本；前端不承担状态推进规则 |
| 作品、卷章和续写位置 | 现有实体/事实及创作页 | 提供作品语义的读模型和分页导航；不要求作者从所有设定实体里挑下一章 |
| 设定与资料能力 | application/knowledge、类型定义和事实 | 由创作任务按需检索与回写；保留独立资源治理入口，避免把实体种类硬编码成新表 |
| 存储与数据库生命周期 | persistence及共同测试执行器 | 保持一个正式库和一个同连接的正式库-test，范围隔离不等于另建数据库 |
| 配置 | config及ncc_shared配置装配 | 默认值、环境覆盖、私有值、模板归属明确；路径只定义一次，读配置不改进程全局环境 |
| 传输和界面 | API、CLI、MCP及前端features | 复用应用服务；MCP只读，非MCP完整读写；界面使用作者语言，基础设施参数留在管理层 |

源码归属的现行细节只在[代码归属规范](../../engineering/code-layout.md)维护。本方案不预先新建大量空目录、通用服务层或表；新增文件必须有实际职责和调用方。

DBA在每批数据变更中另列：已确立事实和候选的边界；世界时间/记录时间及历史保留；跨范围引用/秘密过滤；事件、事实、修订和投影的一致性；连接池/任务并发/超时；追加迁移及失败回退。新增索引、向量能力和性能承诺基于实际查询及数据规模，不先安装未用扩展。既定PostgreSQL主机、端口、账号和库名不在设计时重选。

## 5. 接入开发流程的实现

沿用既有阶段：D1记录产品目标与四职责适用性；D2落实交互、契约和数据变更计划；D3实现；D4以作者任务和数据库边界验证；D5独立核对需求与证据。配置修正等局部任务在同一任务记录中提交短结论，跨模块升级才拆分工件。

工程角色注册在独立development域，触发、读取和必交付字段单源维护；角色profile供宿主发现及ncc-dev派单。共用脚本在原任务JSON中记录计划，生成绑定输入摘要的有限派单包，验证实际报告及陈旧状态。现行接口与执行边界唯一见[开发工作流](../../engineering/workflow.md)，不在方案复制命令。

本轮在隔离候选中验证“局部配置修复”“跨模块创作功能”“无数据库文案修改”三类场景，确认按需触发、角色有具体产物、问题会退回且没有职责越界后整合。四类工程角色不进入创作派单；没有代理能力时顺序执行并如实记录。真实代理输出与确定性检查分别留证，不能只以四个文件存在或字段齐全证明能力。

## 6. 分批交付与验收

| 批次 | 具体工作 | 前置条件 | 验收与回退 |
|---|---|---|---|
| A 当前纠偏 | config/.env与模板归位，共享路径、旧文件迁移、MCP重接；完成产品/工程缺口审查 | 已确定配置原则；不需要连库 | 原字节迁移、冲突不覆盖、MCP/非MCP相同配置源；回退代码时按记录迁回唯一私有文件，不恢复第二份配置 |
| B 工程职责接线 | 四角色注册、profile及挂载，ncc-dev按需派单，报告/陈旧检查和三类行为验证；进度见角色任务 | 作者本轮已明确要求执行 | 角色实际提交可核对结论，独立性如实标注；失败保留隔离候选，不影响小说流程 |
| C 作品与卷章路径 | 明确书、卷、章导航和当前续写位置；普通写作按内容类型选默认评分；资料在上下文中调用 | 产品路径及只读/写入契约先冻结，职责接线可顺序执行 | 超过200章仍能定位和续写；无需打开定义中心；相关界面真实操作通过；可回退读模型和页面、不删除原实体 |
| D 自动化与资源回写 | 核对后台与既有创作闸门、版本、评分、授权；失败恢复和资源异步回写 | 既定数据库连接、代表合成作品及可用模型或明确替身边界 | 生成/人工并发不覆盖，授权一次且范围有效，失败可恢复，重复回写不重复事实；保留原稿与历史 |
| E 作者任务验收 | 立书、续写、直接编辑、修改设定、评分采用、暂停恢复、独立资料治理 | C/D和真实环境就绪 | 用实际路径记录成功率、人工操作、异常恢复及耗时；尚无基线时先测量，不编造提升比例 |

例行续写的目标路径是“一次指令 → 自动处理 → 推荐成果 → 一次采用”，已有有效托管授权按其范围运行。立书的书魂、关键剧情等作者决策仍遵循现有规则，不为了减少点击删除必要创作判断。资源治理可独立运行；普通写作不能被迫先维护全部设定。

角色接线不启动或创建数据库，不改写已有评分判据，不实施C–E，不发布新版本。当前配置来源缺失、真实PostgreSQL联调及五宿主新会话等待验证，不能由角色接线消除。

## 工程专业技能与资产归属

四工程角色各自绑定独立专业skill：需求与产品决策、交互与可用性、架构与安全演进、数据与运维。每个技能包含短入口、可执行SOP、专题方法、工件模板和已核对的原始资料索引；角色职责文件保留边界，方法不复制到agent或docs。共同案例归ncc-dev/references，项目设计/任务/证据仍在docs。

注册表development的skill/resources是唯一角色映射，读取通过共用role_reads解析，与预算、派单和来源新鲜度复用；工程技能独立发现，不要求新增创作命令。校验角色技能存在、资源归属、项目级挂载及包绑定，不以目录存在代替专业能力。

实施：先构建四技能及来源→集中映射/资料迁移→补技能发现与派单反例→运行脚本/静态与真实专业任务→独立审查→按既有授权整合。验收要求四角色能按SOP产出对应工件、处理专题问题并给证据/待验；保留原十二创作角色、配置/双库和评分授权。回退只本批技能/注册/挂载与迁移资料，不涉及数据库。后续C–E产品功能仍不在本批。
