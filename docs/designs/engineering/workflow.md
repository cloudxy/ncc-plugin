## 目的与不可变约束

为 ncc-workflow 本身的维护、规则调整和架构升级建立可恢复、可验证的开发流程。成功应体现为：明确的请求能直接推进；需要作者判断的选择有依据；中断或换 CLI 后能继续；交付结论能对应实际验证的版本。

继承作者已确定的架构，不再重新讨论：

- ncc-workflow 就是日常创作工作区与插件开发现场，保持单仓扁平结构。
- 五端接入保持项目级。zcode 使用独立 Git 克隆；ncc-workflow 与该克隆都可修改，经 GitHub 汇合。每个任务指定一个活动工作树，同一任务避免双边并改。
- GitHub main 是共同集成基线；本地未发布的改动是候选，不冒充已集成版本。
- 书稿与素材永不入远端。开发文档、评测日志、任务记录也不能夹带真实书稿或完整私人会话。
- 创作分支继续使用原有书魂、场景卡、写审分离、盲读和质量闸门。开发分支治理流程变更；grill 不进入小说创作循环。

创作仍遵守“下限靠系统，上限靠作者与选择”：可判定的硬约束需要检验，文风、人物魅力与书魂选择保留多版比较和作者判断，不包装成绝对分或确定性测试。

本方案建立开发流程，但允许以后通过该流程改进创作规则。两条分支由变更提案与评测证据连接，不能因为分支隔离而免除创作规则的行为回归。

## 问题到设计的对应

| 原方案缺口 | 升级决策 |

## 术语与职责

开发阶段使用 D0–D7，避免与创作阶段 S0–S5 混淆。开发者是本任务执行者，作者是产品与创作标准的决策者，评审者是独立核查者。小说十二角色继续按原职责工作，不把 continuity 或 writer 强行当代码评审者。

作者决定目标、创作标准、实质范围取舍与需确认的风险。开发者查事实、提出推荐、执行已授权工作并提供证据。独立评审者报告缺陷和未覆盖项，不代替作者选择，也不把自己改过的版本宣称为独立审查通过。

## 三条任务路径

分类依据是未知性、影响面与可逆性，不按改动行数判定。规则改动是风险标签，可以叠加在局部或结构路径上。

| 路径 | 适用情况 | 必需工件与推进方式 | 终点 |
|---|---|---|---|
| 探索 spike | 验证一个未知问题，暂不保留生产实现 | 任务记录中的问题、探针、观察与推荐；临时产物隔离 | 有证据的结论；转成正式实现时重新定范围与计划 |
| 局部 bounded | 现有行为内的局部修复、文案或接线调整，接口与数据契约稳定 | 一份任务记录，含简短书面计划、验收、验证与交付状态；无需独立 spec | 候选验收完成，或按授权发布 |
| 结构 architectural | 新开发入口、跨宿主契约、状态/权限/数据结构变化 | 任务记录链接书面 spec 与分阶段实施计划；设计包含在 spec 内 | 逐阶段验收，最终按授权发布 |

作者已明确要求流程调整和升级写计划，因此局部路径也保留短计划，不能只留口头承诺。纯文案修正不为凑流程编造失败测试。

隐藏复杂度出现时升级路径，回到最早受影响的设计或计划；保留仍有效的事实与决定。禁止为绕过缺失证据降级。若重写了问题、形成独立新任务，则记录拆分理由与承接关系。

本方案的后续实施属于结构路径；本次修订方案的授权不自动等于安装、发布或更改创作规则的授权。

## 作者决定与质询规则

借鉴 grilling 的依赖树：把事实缺口、工程假设和作者选择分开，只问前置条件已经确定、且会改变方案的关键问题。每轮优先一至三项，更多问题先按影响排序；不把全部待办一次塞给作者。

- 已有明确指令和有效决定直接继承，记录来源与适用范围，不重复询问。
- 环境、代码和加载机制由开发者查证。不能查明的事实标成未知，并说明如何验证。
- 推荐写出理由、代价和备选，避免把所有问题包装成诱导性的“是即可”。
- 可逆的常规实现选择由开发者决定并留痕；未经授权的实质范围变化才需要作者决定。
- 结束条件是关键决定已解决、剩余假设可测试、风险有处置。提问树为空不能证明没有遗漏。
- 确认绑定具体工件和范围。影响目标、公开接口、创作标准或风险承诺的修改会使相关确认失效；编辑性修订不重置全部确认。

D1 的目标和设计合并成一次可读评审，不再要求先批 spec、再逐段批同一设计、再批分类。实施计划涉及新的关键取舍时才另行确认。创作规则改动仍严格执行 AGENTS.md 的“回归后由作者确认”。

## 生命周期与返回路径

以下是结构路径的完整逻辑。局部路径将 D1/D2 合并入任务记录；探索路径只完成 D0、探针与结论。阶段名称不是每一关都要停下来问作者的命令。

| 阶段 | 工作与完成证据 | 未满足时如何处理 |
|---|---|---|
| D0 定位 | 确认活动仓库、工作树、请求、已有决定、任务类别；先跑必要基线，识别既有失败 | 目录或目标有歧义时先查证；保留原有脏改动，不能自动清理 |
| D1 方案 | 问题、目标/非目标、备选、选型理由、接口与数据影响、验收、风险、回滚；关键选择已有决定 | 补关键事实或选择；不凭赞同一句话推断未呈现的决定 |
| D2 计划 | 每步列改动范围、前置条件、验证、回滚与交付范围；标记需作者确认之处 | 发现不可验收步骤就拆小；不先铺一批尚不可执行的流程文档 |
| D3 实现 | 按计划做小批改动；需要行为修复时先复现；规则调整先定义预期与样例 | 新影响回到 D1/D2；实现缺陷留在 D3 修复 |
| D4 验证 | 对确定候选运行全量自测、一致性及适用的行为/宿主检查；保存结果和内容指纹 | 测试失败回 D3；环境受限标记验证受阻，不能写成通过 |
| D5 评审 | 核对意图、实现、反例、边界、验证覆盖和私有内容；报告绑定候选 | 缺陷修复后重验受影响项；无法独立评审时明确写“自查完成，独立评审待办” |
| D6 发布 | 对最终候选确认同步、质量证据与发布授权；提交、推送、记录远端提交；更新干净消费克隆 | 拉取/冲突改变候选时使相关验证和评审失效，返回 D4/D5 |
| D7 观察 | 新会话核验实际加载来源与代表性操作；记录回滚条件和结果 | 文件同步但缓存未刷新时保持“运行验收待办”；新缺陷进入修复/回滚任务 |

关键缺陷必须修复；可延后的非关键意见记录理由、决定人和后续项。私有内容泄露、缺失必要验证和过期证据不能作为普通豁免项清零。

独立评审可以是另一独立会话、作者人工评审或宿主明确提供的评审能力。是否启用子代理遵守当次授权与宿主规则；本流程不把多代理作为五端运行的硬依赖。

## 任务记录与证据新鲜度

拟使用 docs/tasks/<任务号>.md 作为每个任务的唯一进度记录。局部任务把方案与计划直接写在这里；结构任务引用 spec 与计划，不重复其正文。当前路径按文档组织规范归属到用途与模块；来源名不作为目录分类。

每份记录至少包含：

| 内容 | 要求 |
|---|---|
| 身份与状态 | 任务号、目标、路径、风险标签、活动仓库/分支、基线提交；当前 D 阶段、下一步、受阻原因 |
| 决定 | 已授权范围、决定来源、关键取舍与未决问题；结构任务的 spec/计划链接 |
| 变更边界 | 允许修改的路径、禁止触碰的私有内容、其他人的在途改动 |
| 候选 | base commit、相关 tracked/untracked 文件清单与内容指纹、生成物、测试环境与版本 |
| 验证与评审 | 命令、退出码、摘要、报告位置、覆盖范围、缺失项、对应候选指纹 |
| 发布 | 本地验收、提交、远端发布、消费克隆同步、运行加载分别记录；回滚方式 |

指纹由后续拟新增的 scripts/check_dev_workflow.py 计算并核查：按路径排序，包含相对路径、文件内容或软链目标、可执行属性与删除项；包含本任务新增文件，软链所指的仓内源文件也纳入候选；不读取被忽略的小说目录。实际 Git 差异与任务清单比对，未登记的产品改动先报告归属，不能静默排除；他人在途改动单独标记且不擅自纳入本次交付。仅记 HEAD 不能区分未提交改动。证据元数据及其日志不纳入自身指纹，避免自引用；待交付的代码、技能、流程文档与打包文件必须纳入。

同一检查器只验证记录结构、路径边界、文件指纹与缺失证据，不替模型判断设计质量、不把一行“通过”变成事实。用标准库读取任务中的结构化 JSON 证据块，说明性文字保持 Markdown；不新增后台任务引擎或第二份开发状态库。

恢复时先读任务记录，再核对仓库、工作树与候选：无变化则接下一步；变化则列出受影响证据并返回最早失效阶段。对任何候选修改至少重跑适用的确定性检查；语义改动必须补相应行为验证和评审。证据记录本身的补写不使产品指纹递归失效。

## 入口、实现与一事一源

保留“薄入口 + 单一流程文档”的方向，但修正模块解释：调用者是作者，执行者是代理。作者只需描述意图；代理仍须读取实际规则。把文字挪出 SKILL 本身既不能证明复杂度被封装，也不能证明规则会被执行。

| 拟建/调整位置 | 唯一职责 |
|---|---|
| skills/ncc-dev/SKILL.md | 意图与参数、入口边界、定位插件/活动仓库、读取流程文档；不手写第二张阶段表 |
| docs/engineering/workflow.md | 三条路径、阶段与闸门、返回规则、证据契约的唯一规范；按标题按需读取 |
| commands/ncc-dev.md | 宿主命令适配，只转入 ncc-dev，参数不丢失 |
| workflow/registry.json 的 commands.ncc-dev | 命令描述、技能名、参数提示等元数据，供既有生成器消费 |
| .agents/skills、.claude/skills、.claude/commands | 三个仓内相对软链，引用已有唯一实现 |
| docs/tasks/<任务号>.md | 当前任务的进度、决定与证据，不能反向成为全局规则副本 |
| scripts/check_dev_workflow.py | 确定性证据与路径核验，不负责模型判断或通用工作流编排 |
| scripts/check_plugin.py 与相应测试 | 命令登记反向一致性、接线及可定位性；不宣称验证了宿主运行 |
| AGENTS.md、README.md、docs/guides/usage.md | 开发入口与必要说明，细节引用流程文档 |

允许调整既有脚本与命令元数据；禁止在此建设阶段改创作阶段、闸门、角色职责或判据业务。向既有 commands 增一条开发命令是登记改动，不等于改变创作业务状态机；仍按工作区规定接受规则类检查和作者确认。

当前 check_plugin 只从已登记项正向检查文件，不能发现额外未登记技能/命令。新增入口必须登记，补反向检查；不新建另一份“八技能名单”。build_docs 已遍历 commands，优先复用其描述/参数生成能力。若结构化候选核查需要新脚本，新增范围如上，不再承诺“脚本一律不动”。

删除测试验证的是收益：去掉 ncc-dev 后，是否会让任务分类、恢复和证据判断重新散落在各端与会话；不是比较 SKILL 和文档的字数。

## 五端接入与宿主能力

分别定位 plugin_root（所加载规则与脚本的根）和 repo_root（本任务实际修改的仓库）。不能因技能来自已安装克隆，就在那个目录悄悄执行当前项目的 Git 操作。开始任务显示两者及版本，核验活动工作树属于作者指定项目。

| 宿主 | 本仓已有静态接线 | 后续新会话验收 |
|---|---|---|
| claude | .claude/skills 与 .claude/commands | 发现 ncc-dev、参数转入、定位仓库、读取流程、恢复任务 |
| codex | .agents/skills | 菜单/技能发现及自然语言触发；不预设与其他端完全相同的斜杠语法 |
| kimi | .agents/skills；已有角色接线 | 验证实际技能入口及参数传递；不以目录存在代替运行证据 |
| grok | .claude 兼容接线、.agents/skills；已有角色接线 | 核查重复发现或优先级，确认加载唯一来源 |
| zcode | 独立克隆中的插件打包与技能/命令 | 更新后在项目中新会话核查实际来源、版本、入口及恢复 |

五端验收分别记“通过 / 失败 / 未验证 / 环境受限”。文件存在是静态事实；热更新、缓存刷新、支持的命令语法与项目启用范围需运行确认。不得为消除待办而改成用户级安装。暂不能运行某端时可交付本地候选，不能宣称五端完成。

完整最小验收使用下列固定场景。每端跑代表性入口和恢复冒烟；完整失败场景在可用主宿主运行，不对每端无差别复制所有昂贵评测。

| 场景输入或故障 | 应观察到的行为 |
|---|---|
| “验证能否在某端发现项目技能，先不保留实现” | 进入探索，输出探针与结论，不自动变成生产安装 |
| “修正现有命令的一处参数提示，按已有约定处理” | 局部路径，短书面计划与适用检查，不重复确认已定约定 |
| “新增跨端开发入口与任务恢复” | 结构路径，spec/计划明确接口与验收，不能按一文件小改放行 |
| 在 D3 后结束会话，再从另一端继续 | 读任务记录并核对候选，沿用有效决定，不重新问全部背景 |
| 验证报告生成后再改一行技能规则 | 原指纹失效，返回验证/相应评审，不沿用旧通过记录 |
| 测试返回失败、模型报告缺一份或目标 CLI 不可用 | 分别记录失败/缺项/环境受限，不能统一报“全绿” |
| 提交前远端变化，合并修改已验证内容 | 同步后重新取证；消费克隆脏改动不被强制覆盖 |
| “接着写第十章” | 使用创作入口，不触发开发质询与开发阶段审批 |

## 验证分层与规则变更

| 层 | 适用变化 | 完成证据与限制 |
|---|---|---|
| 确定性 | 按实际影响范围 | 文档查内容/链接；局部与新功能测受影响接口；大范围改造才跑全量。需要时运行一致性/生成检查；记录实际测试数 |
| 开发行为 | 开发路由、恢复与交付语义变化 | 固定场景输入，检查受影响行为；无语义变化的文档编辑不重跑代理场景 |
| 创作行为 | 创作标准、闸门、角色职责或判据的实质改动 | 对受影响行为做针对性案例；审稿判据变化时跑 ncc-eval，规则候选验证后作者确认；文字和路径不触发模型回归 |
| 宿主运行 | 入口、链接、打包、定位、缓存 | 新会话读取来源与代表性调用；与静态检查分开 |

大范围改造的确定性检查入口（局部任务按需选择）：

```bash
python3 -m unittest discover -s scripts -p 'test_*.py'
python3 scripts/check_plugin.py -v
python3 scripts/build_docs.py --check
python3 scripts/ncc_eval.py mech
```

代码行为修复先复现缺陷，再验证修复；纯文案、链接和打包声明用相应一致性检查，不强求伪造红绿测试。新增开发检查器的测试至少覆盖陈旧指纹、缺文件、未登记入口、断链和越界路径等真实失败，而非镜像实现。

“埋错先行”只用于适合锚定章的创作判据调整：在改规则前冻结新错例、原有错例、干净对照与通过条件，记录旧行为。不能改完再调答案迎合结果。模型评测是行为比较，不保证同一条新规则一定从红变绿。

完整模型回归使用既有 ncc-eval 的 prepare → 独立盲审报告 → score，固定基线与候选的锚定章/答案、模型及配置，默认每章三次。答案不进入评审上下文。报告完整性、检出/定级/结论准确率、干净章误报、稳定性都要审查；预先写明允许差异和异常处置。

当前 score 生成报告不等于通过：缺报告仍可能正常退出；mech 只证明机械检查；gate 只比较其支持的覆盖层。流程必须审查缺项和前后结果，不能把退出码 0 当所有模型行为通过。ncc-dev 的分流/恢复也不在现有锚定章覆盖范围，要用开发行为案例补足。

第一次增设 ncc-dev 的历史验证保留于发布证据。今后测试采用作者 2026-10-16 明确的影响范围原则，不仅因文件位于 skills 中就重跑无关模型回归；开发入口由实际开发行为案例验证。必要的独立盲审无法完成时保留待验，不捏造报告。

## 同步、发布与回滚

一事一源区分三个层次：规则有唯一权威定义，main 有共同集成历史，任务有唯一活动工作树。多个 Git 克隆可以协作；唯一事实源不等于只能存在一个可编辑物理目录。

交付按实际状态分开：本地候选验收 → 提交完成 → 远端发布 → 消费克隆更新 → 运行加载验收。未授权发布的任务停在可评审候选；发布失败不抹去本地成果，也不能报发布完成。

发布顺序：

1. 检查活动工作树与暂存内容；确认 core.hooksPath 指向 .githooks。配置不随普通 Git 克隆自动启用，消费克隆若承担开发也需检查。
2. 先拉取并按仓库策略合并远端。脏工作树或冲突先处理；保留他人在途改动，不自动 stash、reset 或覆盖。
3. 对合并后的最终候选复核指纹，运行适用验证与评审，再精确暂存任务范围并提交；不使用全目录 add 掩盖边界。
4. 钩子若因远端再次领先阻止提交/推送，重新同步；合并改变内容就重新验收，不能拿合并前报告放行。
5. 推送后核对远端已接受的具体提交。在消费克隆干净且无分叉时按快进方式更新；否则记录冲突/本地工作并协调，不强制重置。
6. 核查已验收提交、消费克隆工作树及新会话加载来源。两个 HEAD 相同只是其中一条证据。

既有钩子检查远端祖先关系及暂存路径标记，不执行全量测试、独立评审、模型回归或内容级隐私扫描；其“先拉”条件也不保证两边完全相同。路径守卫不能发现被贴进公开 Markdown 的书稿，所以任务记录和报告还需内容复核。

不采用 --no-verify 绕过建议。误拦时先核实内容、修正守卫并验证，再走正常提交；网络失败保持未发布。若以后需要增强钩子强制验证，另列独立任务，不在文档里宣称已实现。

回滚使用已发布提交的可审计 revert，重复同步与验证；消费克隆更新至回滚提交并重启/刷新加载。真实书稿、台账与作者素材不在开发回滚范围，不能靠回滚代码倒带小说数据。发生私有内容风险时立即停止发布，先处置风险再继续。

## 外部方法的取舍

外部项目作为设计参考，内置流程在没有这些插件的宿主上独立执行。来源、作者与按需下载说明集中在 [设计出处与致谢](../../../ACKNOWLEDGMENTS.md)，本方案只记录当次机制、取舍与落点，不维护第二份来源目录。参考项目不进入 NCC 的受管依赖、插件打包、CI 安装要求，也不新增 vendor、锁文件、更新器或自动同步。

设计时可按当次授权使用开发者已安装的第三方能力；实际调用需说明项目/技能、版本或文件指纹、用途、影响的决定与工件。单纯阅读参考明确记为阅读，不能写成已经调用或验证。产出的方案与方法由 NCC 自己维护，后续使用者不必安装同一外部项目，第三方流程也不因此取得 NCC 的阶段、权限或状态控制权。

| 来源 | 吸收的思想 | 不引入的默认动作 |
|---|---|---|
| superpowers brainstorming / writing-plans | 先明确意图、按影响分流、计划有验收 | 每段审批、自动提交文档、强制使用特定执行模式 |
| codebase-design | 用调用者所需知识衡量接口、删除测试、真实差异处才设 seam | “拆成长文档就深了”、五端尚未验证就承诺可替换适配器 |
| grilling / grill-me | 决定有依赖，事实先查证，关键选择给推荐与代价 | 无限穷举、一次全问、默认诱导同意、强制子代理 |
| grill-with-docs / domain-modeling | 关键术语与长期决定随讨论落档 | 每个小改建一组 ADR、把工程质询插进书魂与文风选择 |
| to-spec | 把已知上下文综合成可验收规格 | 本地已读版本含发往 issue tracker 的动作，不作为透明替换执行 |
| TDD / verification / code review | 可复现缺陷、对实际候选取证、独立核查 | 文案也强制红绿、用自查冒充 fresh 评审 |

本次参考来自本机已安装文件，审查记录保留内容指纹，仅进行阅读分析，没有执行这些外部技能。用户可自行下载上游学习或在自己的环境中启用；NCC 的默认阶段不调用第三方技能。具体正文、模板或词表的借用需在出处记录中单独说明，不能仅用“思想参考”概括。

## 分阶段实施与退出条件

每阶段交付一个能运行的纵向切片，不先做全部文档、再做全部接线、最后才发现无法验证。

| 阶段 | 实施内容 | 验收与停止条件 |
|---|---|---|
| P0 契约冻结 | 确认本稿关键决定；形成任务记录和分阶段计划，记录各端可用条件与基线 | 范围、授权、验证与回滚可读；已知失败有归属，不能归咎于后续实现 |
| P1 最小可执行入口 | 流程文档、薄技能、命令登记、三条软链、必要生成物和指针；扩展 check_plugin 的登记/链接核查 | 可用主宿主完成一个局部任务；创作意图不误路由；确定性检查通过 |
| P2 恢复与失败闭环 | 任务证据块、内容指纹检查器、相应真实失败测试、开发行为场景 | 换会话能恢复；候选变化被识别；缺验证不报完成；同步冲突能返回正确阶段 |
| P3 规则与宿主验收 | 针对性开发行为回归、受影响宿主冒烟、独立评审和作者规则确认；审稿判据变化再加 ncc-eval | 分层结果与覆盖范围齐全；未验证项保留，不宣称全端完成 |
| P4 授权交付与观察 | 同步最终候选、重新验证、提交/推送、更新独立克隆、刷新加载；演练回滚路径 | 具体远端提交可追溯；目标宿主确实加载该版本；失败可恢复 |

项目级软链会使规则文件修改立即可见，因此规则候选优先在临时测试工作树中实现和评测，确认后再整合回活动主工作树；普通创作会话继续使用已确认版本。临时隔离不改变 ncc-workflow 的终态扁平架构。P1/P2 中间成果可以验证和评审，不在 P3 规则确认前作为已生效规则发布。保留本项目原有七技能与十二角色；只增加开发入口，不把这次建设顺带扩成创作体系重构。

## 完成判定

实现完成必须有证据证明：薄入口能调用本地规范；三条任务路径确实不同；已授权要求不被反复询问；中断可恢复；陈旧证据不能放行；规则回归与开发行为验证各自有覆盖说明；私有内容无外泄；交付报告准确区分候选、发布、同步与运行状态。

本次方案修订完成只表示设计已更新并经文档检查。后续实施、规则确认与发布的结果必须另记，不能用这份 spec 的存在代替。
